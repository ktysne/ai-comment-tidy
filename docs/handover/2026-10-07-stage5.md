## clean の実装と検証

束の選択、削除前の確認、削除処理を分け、全件の確認と削除直前の再確認を行う。
Git は `execFileSync` に引数配列を渡して呼ぶ。
既存の `validateBatchWorktree` と管理パスの検証を使い、`run --fresh` が使う既存の削除処理への影響も確認する。
リンク解除と削除では `lstat` を使い、リンク先へ降りない。
リンクの走査で入れ子のリポジトリや通常ファイルの存在を調べるときも、リンク先を読まない。
登録だけが残る場合に対象を限定して片付けられるか、Windows の空のディレクトリが残る場合に Git の登録がどうなるかは、実際の一時リポジトリで確認して実装方式を決める。
安全に対象を限定できなければ登録を勝手に消さず、具体的な理由と残ったパスを報告する。

| 検証 | 確かめること |
|---|---|
| 通常削除と再実行 | 取り込み済みの束だけ消し、状態と証拠、別の束、外部ファイルを残す |
| 束の指定省略と回の指定 | 選択した回の applied だけを選ぶ。force でも対象を増やさない |
| dry-run | 同じ確認と対象表示を行い、通常ファイル、リンク、登録、状態を変更しない |
| 未取り込みと委譲中 | 通常は拒否し、force は明示した停止済みの未取り込み束にだけ効く |
| 不正な所有関係 | 親とルートのリンク、別リポジトリ、ブランチ、HEAD 変更、ロックを拒否する |
| 担当外の変更 | ステージ済み、未ステージ、未追跡、Git が無視するファイルを含め、削除前に拒否する |
| サブモジュールと入れ子のリポジトリ | 外の登録や内容を変更せず拒否する |
| 内部のリンク | 外部ディレクトリへのジャンクション、ファイルのリンク、壊れたリンクの先を変更しない |
| リンク解除の失敗 | その束の通常ファイルの削除を始めない |
| 複数束の失敗 | 確認失敗なら全件を保持する。削除途中なら進捗と残りを返す |
| Windows の残留 | 空だけ残った場合とファイルが残った場合を区別し、対象だけを再処理できる |
| 名前と行末 | 空白と非 ASCII のパス、CRLF、BOM を持つ担当でも選択と差分判定を誤らない |

削除処理のテストはテストが作った一時ディレクトリだけを対象にする。
段階 4 の既存の試行先や、本物の開発用 worktree は片付けの検証で削除しない。
リンクを作成できない環境ではそのテストを理由付きでスキップし、Windows 実機での確認を残す。
必須の確認は lint、関連テスト、全体のテスト、差分の空白検査、クロスレビューである。

## 2 束の並行試行

担当ファイルが重ならない 2 束を持つ小さな隔離リポジトリを用意する。
片方を CRLF、もう片方を LF とし、基準の写しとハッシュを `run` で用意する。
既定の `implementer.parallel=2` を目安に、メインセッションが一つずつ `delegate` し、実行者を起動する。
2 本が実際に同時に動いた時間を記録し、単なる直列試行と区別する。
実行者は `impl-standard` の定義と生成依頼文に従い、担当だけを編集してオフライン検査を行う。
Codex セッションでは開発者が承認したネイティブサブエージェントの代替経路を使えるが、指定窓口と共有アカウントの検証としては扱わない。

報告の取り込みとメインセッションの監査、通常検査、統合先への `apply` は一件ずつ行う。
片方の取り込みが終わったとき、他方の作業ツリー、状態、実行 ID、基準の写しを変えていないことを確認する。
同じ束の報告取り込みや取り込みを同時に起動しない。
最後に `clean --dry-run` で対象を確認し、試行用リポジトリに限って `clean` を実行して状態と証拠が残ることを確認する。
2 本の起動記録、最終報告、検査結果、状態、変更前後のバイト列、片付けの結果を保存する。
この試行は一度の小さな束に限られるので、共有アカウントの上限や一般の最適な同時数を判断して既定値を変えない。

## 指定窓口と利用上限時の検証

Claude セッションで窓口の最新の定義と、待ち合わせや停止の手順を確認してから行う。
実行 ID が返る前と後の中断、完了報告の取得、監査行の一致を確認する。
実行者が使えなくなったときは追加の束の起動を止め、実行中の束を勝手に取り消さない。
各窓口の実行結果から停止または完了を確認し、記録済みの ID で報告を回収するか、停止した束を取り消して再開する。
利用上限を意図的に消費して発生させず、制御した失敗入力で状態と再開の手順を確認する。
実際の上限発生を観測していなければ、窓口側の停止と再委譲が実測済みであるとは記録しない。
失敗入力を使った検証と、本物の共有アカウントで観測した結果は分けて保存する。
