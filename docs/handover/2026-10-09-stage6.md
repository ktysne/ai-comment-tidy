## 決定済みの判断

| 項目 | 決定 | 理由 |
|---|---|---|
| hunk の作り方 | 束の作業ツリーで `git diff -U3 --no-renames <基準>` を担当ファイルに限って取る | 移行元と同じ形で、行末の変換を Git に任せられる。自前で差分を取ると、依存なしで差分の算法を持つことになる |
| コメントの行の判定 | 削った行は基準の、足した行と前後の行は作業ツリーのファイルを `commentBlocks` で読み、行番号で決める | 行頭の記号で決める移行元は、文字列の中の `//` やコードと同じ行のコメントを取り違える |
| 対象の状態 | 「報告あり」と「検査済み」。状態は変えない | `check` の前にも後にも材料を読めるようにする。監査は材料を出すだけで、合否を持たない |
| `apply` との関係 | `apply` は監査の実行を求めない | 監査済みの記録を状態に足すと状態の形が変わり、材料を読んだかは道具から確かめられない |
| 出力 | `audit-<束>.md` と `audit-<束>.json` | 人は Markdown を読み、段階 7 の PR 本文の表は JSON を読む |
| 束をまたぐ集約 | この段階では作らない | 報告の JSON の候補は `status` がすでに束をまたいで出している。検査の該当の集約は段階 7 の表で扱う |
| 重点ファイル | 移行元の `CRITICAL` は持たない | 設計資料に無く、rec-studio に固有の規則である |

## 順 1: 既定の検査と材料の出力

`src/audit/` に、hunk の抽出、検査、材料の書き出しを分けて置く。
入口は `src/audit/command.js` とし、`src/cli.js` に `audit` を足す。
束の定義、状態、作業ツリーの検証は、`check` と `apply` が使う既存の関数を使う。
差分は `execFileSync` に引数配列を渡して取り、担当ファイルだけをパスの指定に渡す。

重要語の既定の語群は、移行元の語群から rec-studio に固有の語(外部 API、オーディオ、メッセージスレッドなど)を除いた次の語から始める。

| 語群 | 既定の語 |
|---|---|
| スレッドと寿命と順序 | スレッド、ワーカー、atomic、ロック、排他、再入、寿命、破棄、解放、所有、中断、先に、してから、必ず、してはならない、ブロック、待たない、同時 |
| 数値と単位 | epsilon、丸め、Hz、ms、秒、バイト、px、上限、下限、空なら、0 なら、null |
| 互換 | 旧形式、旧キー、旧版、schemaVersion、互換 |
| 撤去条件 | 削除可能、削除できる、TODO、FIXME、追跡 |

`ms` と英字の語は単語の境界で照合し、識別子の一部に当たらないようにする。
設定の `audit.keywordGroups` は、同じ名前の語群には語を足し、新しい名前なら語群を足す。

| 検証 | 確かめること |
|---|---|
| hunk の抽出 | CRLF と BOM の担当、文字列の中の `//`、コードと同じ行のコメント、複数行のコメントで、行の判定を誤らない |
| 担当の限定 | 担当外のファイルの差分を読まない。担当ファイルが変わっていなければ該当なしで材料を書く |
| 重要語の消失 | 足した文、同じファイルの他のコメント、参照先の資料のどれかに残っていれば拾わない |
| 丸ごと削除 | 4 行以上を削って足した文が無い hunk だけを拾う。空行と `licensePatterns` のブロックは数えない |
| 逃げ言葉と参照 | 足した文の逃げ言葉と、実在しない見出しへの参照を拾う。参照の照合は `src/docs-refs.js` を使う |
| 状態と入口 | 「報告あり」と「検査済み」以外は拒否し、状態ファイルを変えない。作業ツリーの検証に失敗したら材料を書かない |
| 出力 | Markdown と JSON が同じ該当を持ち、削減率と報告の JSON の候補を含む |

## 順 2: 誤りの型の検査

設計資料「誤りの型の検査」の 6 種を足す。
語の抽出は依存を持たないので、カタカナの連なり、英数字の識別子、2 字以上の漢字の連なりを語とみなす。
「元に無い語」は、同じ hunk の削った文、ファイルのコード、参照先の資料に無い語を拾う。
「近くの宣言への混入」は、ある hunk で削られた語が、その hunk で足されず、同じファイルの別の hunk で足された場合を拾う。
この 2 種は材料に並べるだけで、件数の要約では他の検査と分けて出す。

| 検証 | 確かめること |
|---|---|
| 未決の消失 | 削った文の「仮決め」「未決」「TODO」「判断事項」が足した文に無い hunk を拾う |
| 括弧の対応 | 足した文の丸括弧、鉤括弧、角括弧の開きと閉じの数が合わない箇所を拾う |
| 同じ行の重複 | 同じ本文の行が、1 つのファイルの複数の hunk に足された場合を拾う |
| 自己参照 | ファイルの最初のコードより前に足された文が、「このファイル」「本ファイル」などで自身を指す場合を拾う |
| 誤検出の抑え | コードの識別子と参照先の資料の語は「元に無い語」にしない |

## 順 3: 監査の試行

段階 5 と同じく、セッションの作業ディレクトリの中で Git が無視する場所に試行リポジトリを作る。
既定の検査と誤りの型に当たる変更を、実行者に頼らず作業ツリーへ直接書いて用意し、材料に期待どおり並ぶかを確かめる。
材料を読んで規則を 1 行戻し、`check` をやり直して `apply` するまでを通す。
実行者への委譲を含めるかは、順 1 と順 2 の結果を見て決める。

## 判断待ち

- 順 0 の決定のうち、`apply` が監査の実行を求めないこと、束をまたぐ集約をこの段階で作らないこと、重点ファイルを持たないことは、アドバイザーへの相談が権限の判定で拒否されたため、メインセッションの判断で仮に決めた。計画の PR で確認してほしい。
- 既定の語群は移行元からの仮の選定である。実際のリポジトリでの試行(段階 9)で見直す。

## 落とし穴

- 自動モードでは、Agent ツールの起動(実装の窓口とアドバイザー)が判定で拒否されることがある。委譲の前に権限モードを確かめる。
- 窓口が Codex に `-C` を渡さないことがある([ktysne/claude-codex-bridge#138](https://github.com/ktysne/claude-codex-bridge/issues/138))。実装の委譲はメインの作業用 worktree をセッションの作業ディレクトリにして行うか、依頼文の作業ディレクトリが書き込める範囲にあることを確かめる。
- 束の作業ツリーは `clean` で消えるので、監査は `clean` の前に行う。
