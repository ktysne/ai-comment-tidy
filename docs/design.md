## この資料の範囲

ai-comment-tidy は、既存のリポジトリのソースコメントを、グローバルの「コメント記述ルール」(`C:\Users\mss02968\.claude\CLAUDE.md` の同名の節。例と理由はスキル `~/.claude/skills/comment-writing/SKILL.md`)に適合させる作業のための道具である。
束ごとに AI へ整理を任せ、機械で検査し、メインセッションが監査して取り込む。
あわせて、新しく書くコメントが同じルールから外れないよう、編集の直後とコミットの直前に検査する(`lint`)。
この資料は、道具の目的、全体の流れ、配り方、コマンド、設定、検査と監査の規則、実行者への委譲、実装の段階を定める。
コメント記述ルールそのものの内容は扱わない。

## 背景

rec-studio で、コメントの整理を 2 回に分けて行った(2026-09-18〜19)。
1 回目は経緯、出所、Issue 番号、時期ラベルの除去で、2 回目は量と置き場所の規定(3 行の上限、設計資料の再説明の禁止、非公開の宣言の doc コメントの禁止など)への適合である。
2 回目は 34 束に分けて Codex に整理させ、メインセッションが監査して取り込んだ。
コメント文字数は 1,215,451 から 719,918 へ(−40.8%)、`///` の行は 16,696 から 5,675 へ(−66.0%)減り、コードのトークンは 1 つも変えていない。

このときの道具は rec-studio の `tools/comment-pass2/` にあり、次の制約があった。

- 言語が C++、JavaScript、CMake、bat に固定され、監査の重要語と対象のパスが rec-studio に合わせて書かれていた。
- 束の実行(作業ツリーの作成、依頼文、Codex の起動、完了の待ち合わせ、検査、取り込み、コミット)を、メインセッションが毎回手で回していた。
- Codex のサンドボックスでは git を呼ぶ検査が動かず、束の検査はメインセッションでしか回せなかった。
- 監査では、機械で拾えるはずの誤りを毎回人が見つけて直していた。

他のプロジェクトでも同じ作業を順に行う予定なので、これらを汎用の道具にまとめる。
移行元のファイルと、この道具の各部分の対応は、末尾の「移行元との対応」にある。

## 目的と目的としないこと

目的は次のとおりである。

- どのリポジトリにも、設定ファイルを置くだけで適用できる。言語は字句解析の追加で増やせる。
- 束の実行を少数のコマンドにし、人が関わるのを監査と取り込みの判断だけにする。
- コメント以外が変わっていないことを、機械で保証する(字句の同一性の検査)。
- 監査で見るべき箇所を、機械の検査で絞り込む。
- PR の本文に載せる数値の表を、同じ道具で作れるようにする。

次のことは目的にしない。

- コメントを書き換える判断そのものを自動化すること。判断は実行者とメインセッションの監査が行う。
- コードの変更(命名の変更、定数化、関数分割)。道具はコメント以外の変更を検出して止めるだけである。
- 作業ツリーの一般的な片付け。これは agent-gc(`D:\Desktop\Develop\agent-gc`)で扱う。道具自身が作った束の作業ツリーの削除だけは、取り込みの記録で判断できるこの道具が行う。

## 用語

| 用語 | 意味 |
|---|---|
| **回** | 1 回分の整理。判定基準が 1 つ対応する。例: 経緯の除去の回、量と置き場所の回。設定では `passes` のキーで識別する |
| **束** | 実行者に 1 回で任せるファイルのまとまり。1 つの束は 1 つの領域に収める |
| **領域** | PR を分ける単位のディレクトリのまとまり。例: `engine`、`io`、`tests` |
| **基準コミット** | 回の開始時に固定するコミット。束の作業ツリーはここから作り、束の検査はここと比べる |
| **統合先** | 束の結果を写す作業ツリーとブランチ。回ごとに 1 本で、PR は領域ごとにここから切り出す |
| **実行者** | 束の整理を行う AI。既定は Codex で、メインセッションが Agent ツールの窓口(`impl-standard`)を経て渡す |
| **判定基準** | コメント記述ルールを、そのリポジトリへ当てはめる細則。回ごとに 1 つ |
| **監査** | 束の結果を取り込む前に、消えた情報や誤りをメインセッションが確かめること |

## 全体の流れ

1 つの回は次の順に進む。

1. `init` で設定ファイルと判定基準の雛形を作る。メインセッションが、対象のパス、言語、資料の置き場、領域、判定基準の細則を書く。
2. `plan` で基準コミットを固定し、束を作る。基準コミットと束の定義は追跡するファイルに書く。
3. メインセッションが統合先のブランチを基準コミットから作る(`git switch -c comment-tidy/<回> <基準コミット>`)。
4. `run` で束の作業ツリーと依頼文を用意する。メインセッションが、`delegate` で委譲中を記録し、Agent ツールの `impl-standard` を背景で起動して依頼文を渡し、完了の通知を待つ。最終報告は `report` で取り込む(後述「実行者への委譲」)。
5. `check` と `audit` で束を検査し、監査の材料を出す。メインセッションが監査する。
6. `apply` で統合先へ写す。監査で見つけた誤りは統合先で直し、束ごとにコミットする。
7. すべての束の後に、回ごとの仕上げを行う(例: 非公開の宣言の doc コメントの記号の置き換えは `privatize`)。
8. `branch` で領域ごとのブランチを切り出し、`table` で PR の本文に載せる表を作って、PR を出す。
9. `clean` で道具が作った束の作業ツリーを消す。

途中で中断しても、`status` で束ごとの状態が分かる。
`run` は作業ツリーの状態から、新規と再開を書き分けた依頼文を作る。
束ごとの状態の正本は `status` である。agent-cockpit のタスクには、回の段階(計画、実行、監査、PR)だけを載せ、束ごとには載せない。

## 配布の形

道具は中央の 1 か所(`D:\Desktop\Develop\ai-comment-tidy`)に置き、対象のリポジトリへ向けて実行する。
対象のリポジトリへは道具のコードを取り込まない。
整理の回は一時的な作業なので、道具を各リポジトリへ取り込むと、取り込みと削除のたびに PR が要り、道具の修正も各リポジトリへ同期し直す必要がある。
`lint` は回が終わった後も使い続けるが、グローバルのフックから中央の道具を呼ぶので、これも各リポジトリへは取り込まない。

対象のリポジトリに置くのは、次のものだけである。

| 置き場 | 内容 | git |
|---|---|---|
| `.comment-tidy/config.json` | 対象のパス、言語、資料の置き場、領域、実行者、回の定義、`lint` の設定 | 追跡する |
| `.comment-tidy/criteria-<回>.md` | そのリポジトリへ当てはめる判定基準の細則 | 追跡する |
| `.comment-tidy/batches-<回>.json` | 基準コミット、道具の版、束の定義 | 追跡する |
| `.comment-tidy/work/` | 集計、依頼文、実行者の報告、監査の材料、基準の写し、束の状態 | 追跡しない |
| `.comment-tidy/worktrees/` | 束の作業ツリー | 追跡しない |

追跡しない 2 つは、`init` が `.gitignore` に足す。
判定基準と束の定義を追跡するのは、レビューで読めるようにし、別のセッションから再開できるようにするためである。
回がすべて終わったら、判定基準と束の定義を消す PR を出す。
`config.json` は `lint` が使い続けるので残す。

`batches-<回>.json` には、`plan` を実行した道具のコミットを記録する。
集計の値は字句解析の版で変わるので、`table` は記録と違う版で実行されたら警告を出す。

メインセッション向けの手順は、グローバルのスキル(`~/.claude/skills/comment-tidy/SKILL.md`)として配る。
スキルは、この資料の「全体の流れ」と「監査」を、Claude Code が従う手順として書いたものである。
コメント記述ルールの例と理由は `comment-writing` スキルが持つので、`comment-tidy` スキルはそれを参照するだけにする。
`comment-tidy install-skill` がこの写しを置く。

## 実装の前提

- Node.js 20 以上、ESM。実行時の依存パッケージは持たない。テストは vitest、lint は eslint を devDependencies で使う。
- テストと lint の実行には、Node.js 22.12 以上が要る(vitest と eslint が求めるため)。道具そのものは 20 以上で動く。
- 入口は 1 つ(`bin/comment-tidy.js`)で、サブコマンドで分ける。
- 対象のリポジトリは `--repo`(既定はカレントディレクトリ)で指定する。設定ファイルの既定は `<repo>/.comment-tidy/config.json` で、`--config <絶対パス>` で差し替えられる。どのコマンドも同じ形で受ける。
- git は `child_process.execFileSync` で呼ぶ。`check --offline` は git を含め子プロセスを一切起動せず、作業ツリーの外へ書き込まない。Codex のサンドボックスでは、起動されたコマンドがさらに子プロセスを起こすと `spawn EPERM` で失敗するためである(claude-codex-bridge の docs/gpt-agents.md「既知の制約」)。
- 設定の中のパスの先頭の `~` は、道具がホームディレクトリへ展開する(`execFile` はシェルを通さないので展開されない)。

## 設定ファイル

`.comment-tidy/config.json` の形は次のとおりである(値は例)。

```json
{
  "rulesPaths": [
    "C:/Users/mss02968/.claude/CLAUDE.md",
    "C:/Users/mss02968/.claude/skills/comment-writing/SKILL.md"
  ],
  "scope": {
    "include": ["src/**", "tests/**", "tools/**/*.js", "**/CMakeLists.txt", "*.bat"],
    "exclude": ["third_party/**", "tools/cross-review*.js"]
  },
  "languages": {
    "cpp": ["**/*.{h,hpp,cpp,cc,inl}"],
    "js": ["**/*.{js,mjs,cjs}"],
    "cmake": ["**/CMakeLists.txt", "**/*.cmake"],
    "bat": ["*.bat"]
  },
  "areas": {
    "engine": ["src/engine/**"],
    "io": ["src/io/**"],
    "app": ["src/app/**"],
    "tests": ["tests/**"]
  },
  "docs": {
    "root": "docs",
    "refPattern": "docs/(?<doc>[\\w.-]+)「(?<heading>[^」]+)」"
  },
  "maxCommentLines": 3,
  "maxLineWidth": 108,
  "licensePatterns": ["Copyright", "SPDX-License-Identifier", "この表示を残すこと"],
  "implementer": {
    "agent": "impl-standard",
    "parallel": 2
  },
  "plan": {
    "base": "origin/main",
    "maxWeight": 700
  },
  "audit": {
    "keywordGroups": { "外部 API": ["JUCE", "WASAPI"] }
  },
  "privatize": {
    "cpp": { "implementationFiles": ["src/**/*.cpp"], "testFiles": ["tests/**"] }
  },
  "passes": {
    "history": { "criteria": "criteria-history.md" },
    "volume": { "criteria": "criteria-volume.md", "finish": ["privatize"] }
  }
}
```

- `scope` と `languages` が、集計、検査、束の対象を決める。`scope.include` を書かなければ、リポジトリ全体を対象にする。
- パターンは glob で書く。`*` と `?` は `/` をまたがず、`**/` は 0 個以上の階層に当たり、`{a,b}` は候補のどれかに当たる。`/` を含まないパターン(`*.bat`、`third_party`)は、どの階層の名前にも当たる。フォルダーに当たるパターンは、その下のファイルにも当たる。
- `languages` のキーは字句解析の `id`(`cpp`、`csharp`、`js`、`ts`、`cmake`、`bat`)に限り、知らないキーは設定の誤りとする。`languages` を書けば、拡張子による判定を置き換える。書かなければ拡張子で決める。
- `lint` は `scope.include` を見ず、`scope.exclude` と `languages` だけを使う。フックは回の外でも全リポジトリで動くので、`include` を書いていないリポジトリで黙らないようにするためである。
- `areas` は領域の定義で、`plan` はこれを越えて束を作らない。ファイルは、記述順で最初に当たった領域に属する。2 つ以上の領域に当たるファイルと、どの領域にも当たらない対象のファイルは、`plan` が一覧で知らせる。
- `plan.base` は束を作るときの基準(既定 `origin/main`)で、`plan.maxWeight` は 1 束の重みの上限(既定 700)である。`plan --base <ref>` で、その回だけ基準を変えられる。
- `passes` は回の定義で、回ごとに判定基準の細則(`criteria`)と、すべての束の後の仕上げ(`finish`)を持つ。
- `criteria` の相対パスは対象リポジトリの `.comment-tidy/` を基準とする。`--config` は設定の読み取り先を差し替えるだけで、この基準を変えない。
- `docs.refPattern` は、コメントや資料の中の資料への参照を拾う正規表現で、名前付きの捕捉 `doc` と `heading` を持たなければならない。`doc` は `docs.root` の中のファイル名との前方一致で解決する(`docs/05「節名」` と `docs/05-architecture.md「節名」` のどちらも同じ資料に当たる)。
- `licensePatterns` のどれかを含むコメントのブロックは、行数の検査と監査の対象から外す。
- `audit.keywordGroups` は、道具の既定の重要語(後述)に足す語である。プロジェクトの外部 API や固有の概念をここに書く。
- `rulesPaths` は、依頼文の「必ず読むもの」に載せるコメント記述ルールの正本である。規則の本文(CLAUDE.md の節)と、例と理由(`comment-writing` スキル)の両方を載せる。
- `implementer.agent` は、メインセッションが束を渡す窓口の定義の名前で、依頼文の案内と `status` の表示に使う。`implementer.parallel` は同時に渡す束の数の目安で、`status` が次に渡せる束を示すのに使う。

## 設定の雛形

`init` は次を作る。既にあるファイルは上書きせず、その旨を出して終了コード 2 で止める。
管理用の置き場 `.comment-tidy` またはその要素がリンクの場合、何も書き込まずに終了コード 2 で止める。

- `.comment-tidy/config.json`:追跡しているファイルの拡張子から、見つかった言語だけを `languages` に書く(CMake は `**/CMakeLists.txt` も)。それらのファイルを含む第 1 階層のディレクトリを、`scope.include` と `areas` の初期値に書く。ルート直下に対応するファイルがあれば、そのファイル名も `scope.include` に書き、それらをまとめた領域 `root` を最後に足す。`passes` には `--pass` の回を 1 件書く。
- `.comment-tidy/criteria-<回>.md`:道具の `templates/criteria.md` の写し。
- `.gitignore` に、追跡しない 2 つの置き場の行。

判定基準の細則は、`## 目的`、`## 落とさないもの`、`## 対象外` の 3 つの見出しを必ず持つ。
依頼文は、それぞれの見出しから次の `## ` の見出しまでを埋め込む。ほかの見出しは自由に置いてよい。
雛形は、移行元の判定基準から C++、JUCE、rec-studio に固有の部分を除き、この見出しへ組み直したものである。
雛形が見出しの解析を通ることと、禁止の語を含まないことは、道具のテストで守る。

## 束の定義のファイル

`plan` が書く `.comment-tidy/batches-<回>.json` の形は次のとおりである。

```json
{
  "schemaVersion": 1,
  "pass": "volume",
  "base": "94a9eee0c0ffee...",
  "toolCommit": "abc1234...",
  "batches": [
    {
      "id": "V01",
      "area": "engine",
      "files": ["src/engine/AudioEngine.h", "src/engine/AudioEngine.cpp"],
      "weight": 638,
      "commentChars": 30151,
      "docs": ["docs/05-architecture.md", "docs/09-effects-mixdown.md"]
    }
  ]
}
```

`base` は `plan` を実行した時点の、設定の基準(既定は `origin/main`)を解決した SHA である。
回の途中で main が進んでも比較がずれないよう、以後のコマンドはすべてこの SHA を使う。
`docs` は `plan` が担当ファイルのコメントの参照から集めた資料で、メインセッションが手で足し引きしてよい。
`toolCommit` は道具のリポジトリの HEAD で、取れなければ `null` とする。
`schemaVersion` は形の版で、道具は知らない版のファイルを設定の誤りとして止める。
後述の束の状態のファイルも同じ扱いとする。

## 作業の置き場と束の状態

道具が書く場所は、回と束の名前から次のように決まる。
決め方は `src/paths.js` の 1 か所に置き、どのコマンドもそれを使う。

| 置き場 | 内容 | 書くコマンド |
|---|---|---|
| `.comment-tidy/worktrees/<回>/<束>/` | 束の作業ツリー | `run` |
| `.comment-tidy/work/<回>/base/<束>/` | 基準の写し | `run` |
| `.comment-tidy/work/<回>/base/<束>.hashes.json` | 基準のハッシュの一覧 | `run` |
| `.comment-tidy/work/<回>/prompts/<束>.md` | 依頼文 | `run` |
| `.comment-tidy/work/<回>/reports/<束>.md` | 実行者の最終報告 | `report` |
| `.comment-tidy/work/<回>/check-<束>.json` | `check` の結果 | `check`(`--offline` を除く) |
| `.comment-tidy/work/<回>/state/<束>.json` | 束の状態 | `run`、`delegate`、`report`、`check`(`--offline` を除く)、`apply` |

ハッシュの一覧は基準の写しの外に置き、担当ファイルの名前と衝突しないようにする。

束の状態のファイルの形は次のとおりである(値は例)。

```json
{
  "schemaVersion": 1,
  "pass": "volume",
  "batch": "V01",
  "status": "delegated",
  "runId": "20261010-101500-123",
  "timestamps": { "prepared": "2026-10-10T10:14:00Z", "delegated": "2026-10-10T10:15:00Z" },
  "notes": [],
  "check": null,
  "report": null
}
```

`status` は英語の識別子で持ち、表示の日本語との対応も同じモジュール(`src/state.js`)に置く。
状態のファイルが無い束は「未着手」とする。

| 識別子 | 表示 | 移れる先 |
|---|---|---|
| (ファイル無し) | 未着手 | `prepared` |
| `prepared` | 用意済み | `delegated`、`prepared`(`run --fresh`) |
| `delegated` | 委譲中 | `reported`、`delegated`(`delegate --run-id`)、`prepared`(`delegate --cancel`) |
| `reported` | 報告あり | `checked`、`prepared`(`run --fresh`) |
| `checked` | 検査済み | `applied`、`checked`(`check` の再実行)、`prepared`(`run --fresh`) |
| `applied` | 取り込み済み | なし |

表に無い遷移は、状態を書き換えずに終了コード 2 で止める。
状態を書く `check` は、メインセッションが `reported` か `checked` の束に実行するものだけである。
合格したときだけ `checked` へ移し、不合格なら状態を変えずに結果を `check` に書く。
実行者が委譲中に実行する `check --offline` は、作業ツリーの外へ書き込まないので、状態も結果のファイルも書かない。
`notes` は「監査行なし」「報告の JSON なし」のような、状態に添える記録である。

通常の `check <束>` は束の定義の `base` と束の作業ツリーを比較し、回と束を含む結果を `check-<束>.json` と状態の `check` に保存する。
対象リポジトリに属する基準コミットの detached HEAD の作業ツリーだけを検査する。
合格時の `checked` の時刻は結果の `checkedAt` と同じにする。
不合格時は状態名と状態の時刻を保ち、`check` を最新の不合格結果に置き換える。
以前の検査結果がある場合は、結果ファイルを保存する前に状態の `check` を `null` にして無効にする。
無効化後の保存に失敗した場合は `check` を `null` のまま保ち、次の検査で結果を記録し直す。
以前の結果の無効化に失敗した場合は、結果ファイルの保存を始めず終了コード 2 で止める。
実行 ID、報告、記録は再検査で保持する。

`check <束> --offline` は束の定義、基準の写し、ハッシュだけから検査し、状態を読んだり更新したりしない。
この呼び出しの `--repo` は、束の定義を置いた対象リポジトリのルートを指定する。
Git を使わないため、サブディレクトリからルートを自動で探さない。
基準の写しは担当ファイルの保存済みハッシュと照合してから使う。
束の検査では比較元と担当ファイル、結果の置き場が定義から決まるので、`--base`、`--base-dir`、`--hashes`、`--files`、`--out` の併用は拒否する。
束を取らない既存の明示指定の検査も引き続き使える。

## コマンド

| コマンド | 役割 |
|---|---|
| `init [--pass <回>]` | 設定ファイル、判定基準の雛形、`.gitignore` の行を作る(後述「設定の雛形」)。回の既定は `volume` |
| `stats` | コミットまたは作業ツリーの時点の集計を取る(コメント行、コメント文字数、doc コメントの行、区切り線の行、コード行)。`--compare` で複数時点を領域ごとの表に並べる |
| `plan <回> [--base <ref>] [--force]` | 基準コミットを固定し、束を作る(後述「束の作り方」)。既にある束の定義は `--force` が無ければ上書きしない |
| `prompt <束>` | 束の依頼文を作って標準出力へ出す。作業ツリーの状態から新規と再開を書き分ける。作業ツリーが無くても新規として出せる。`run` も同じ生成を使う |
| `run <束...>` | 作業ツリーの作成、基準の写しの書き出し、依頼文のファイルへの書き出しを行う。実行者は起動しない。`--fresh` は、作業ツリーの途中の変更を捨てて作り直す |
| `delegate <束> [--run-id <ID>] [--cancel]` | 束を「委譲中」にし、窓口が返した実行 ID を記録する。`--cancel` は委譲をやめた束を「用意済み」に戻す |
| `report <束> <ファイル>` | 実行者の最終報告(`codex-agent.sh --wait <実行 ID>` の標準出力)を取り込み、報告の JSON と監査行を読む |
| `status` | 束ごとの状態(未着手、用意済み、委譲中、報告あり、検査済み、取り込み済み)と、担当ファイルの進み具合(コメント文字数の基準コミットと作業ツリーの比)、次に渡せる束を出す。委譲中の束は実行 ID も出す |
| `check <束>` | 束の作業ツリーを検査する(後述「検査」)。`--offline` は git を呼ばず、基準の写しと比べる |
| `audit <束>` | 監査の材料を出す(後述「監査」) |
| `apply <束>` | 検査が通った束の担当ファイルを統合先へ写す(後述「取り込み」) |
| `residue` | 経緯の表現の残りを探す(経緯の除去の回向け) |
| `privatize` | 非公開の宣言の doc コメントの記号を置き換える(後述)。`--verify` で差分が記号だけの違いかを確かめる |
| `branch <領域>` | 統合先から、その領域のファイルの差分だけを持つブランチを main から切り出す |
| `table` | PR の本文に載せる表を作る(後述) |
| `refs` | 資料の見出しへの参照が実在するかを検査する |
| `clean [<束...>] [--dry-run] [--force]` | 選択した回の取り込み済みの束、または明示した束の作業ツリーを消す(後述) |
| `install-skill` | グローバルのスキルを置く |
| `lint` | 新しく書いたコメントを検査する(後述「編集時とコミット前の検査」)。フックと手の両方から使う |
| `install-hooks [--settings <path>] [--dry-run] [--remove]` | `lint` を呼ぶフックを設定へ追加、確認、削除する(既定の設定先は `~/.claude/settings.json`) |

束を引数に取るコマンドは、回を `--pass <回>` で受ける。
省いたときは、束の定義のファイルが 1 つだけならその回とし、2 つ以上あれば引数の誤りとする。
束の名前は回ごとのファイルの中でだけ一意だからである。

終了コードは、0 が問題なし、1 が検査の不合格、2 が引数や設定の誤りとする。
コマンドの中の失敗(例外)も 2 とする。
検査の結果は標準出力に要約を出し、詳細は `.comment-tidy/work/` に書く(`check --offline` は標準出力だけ)。

### 束の状態の表示

`status [--pass <回>]` は対象の回の束を定義順に表示する。
回を省いたときは、束を引数に取るコマンドと同じく、束の定義のファイルが一つだけならその回を選ぶ。
状態は記録から読み、実行者のプロセスは調べない。
ファイルの作成や状態の更新は行わない。

基準のコメント文字数は、束の定義の `base` の担当ファイルを `readMany` でまとめて読み、現在の設定と字句解析で集計し直す。
束の定義の `commentChars` は計画時の値なので、表示の計算には使わない。
現在値は束の作業ツリーから読み、取り込み済みの束は `--repo` の統合先から読む。
作業ツリーがない場合と、担当ファイルが欠落した場合は未計測とし、欠落したファイル名も表示する。
読めない文字コードや対応しない言語は、集計値を出さず終了コード 2 で止める。
基準比は現在値 / 基準値 × 100 で、基準値が 0 または現在値が未計測なら算出不可とする。
基準比はコメント量の比較であり、検査や監査の合格を表さない。

次に渡せる束は、未着手または用意済みの束から定義順に選ぶ。
表示する数は `implementer.parallel` からその回の委譲中の数を差し引いた空き枠までとする。
委譲中の束には実行 ID を表示し、記録がなければ未記録とする。
状態の `notes` と、`report` の `docsCandidates`、`needsDecision`、`codeImprovements` も束の名前とともに表示する。

## 字句解析

字句解析は、ファイルをコード、文字列、コメントの区間に分ける。
集計、字句の同一性の検査、監査、`privatize` のすべてがこの区間を使う。

言語ごとに 1 つのモジュールを置き、次の形を持たせる。

```js
export const language = {
  id: 'cpp',
  lex(source) { /* → [{ kind: 'code' | 'string' | 'comment', start, end }] */ },
  docCommentMarkers: ['///', '///<'],
  separatorPattern: /^\/\/+\s*[=\-*~#_]{4,}\s*$/,
};
```

対応する言語は、C++、C#、JavaScript、TypeScript、CMake、bat である。
`.tsx` は JSX のテキストの扱いを決めるまで対象外とする。
新しい言語を足すときは、文字列の中のコメント記号、生文字列、テンプレート文字列、行継続、BOM と CRLF のテストを書いてから使う。

字句の同一性の検査は、前後のファイルを同じ字句解析に通し、コメントを除いたトークン列と文字列リテラルを比べる。
解析の癖は前後で相殺されるので、構文の正しさまでは検査しない。
トークンは最長一致で区切る(短い記号で区切ると、`>>` と `> >` のような違いを見逃す)。

## 時点の読み取り

`stats` と `check` は、比べる時点を同じ形の読み取り口で扱う。
読み取り口は `listFiles()`(リポジトリからの相対パスを `/` 区切りで返す)、`read(path)`(内容を Buffer で返す)、`readMany(paths)`(パスから Buffer への Map を返す)、`has(path)` を持つ。
コミットは `readMany` で 1 回の `cat-file` にまとめて読む。ファイルごとに git を起動すると、数千のファイルで数十秒かかるためである。
コミットの読み取り口は `readManyRaw(paths)` で変換前の blob をまとめて読み、`changedFiles()` で作業ツリーとの差がある追跡済みパスを返す。
Buffer で返すのは、行末と UTF-8 の検査を呼び出し側の 1 か所で行うためである。

| 実装 | 一覧 | 内容 | 置き場 |
|---|---|---|---|
| コミット | `git ls-tree -r -z` | `git cat-file --batch --filters` | `src/snapshot/git.js` |
| 作業ツリー | `git ls-files --cached --others --exclude-standard -z` | ファイル | `src/snapshot/git.js` |
| 写しのディレクトリ | 引数のファイルの一覧(ディレクトリは走査しない) | ファイル | `src/snapshot/fs.js` |

コミットの内容は、`--filters` でチェックアウトと同じ行末の変換(`text=auto`、`core.autocrlf`、`.gitattributes` の `eol`)を通して読む。
blob のまま読むと、変換が効くリポジトリでは比較元が LF、作業ツリーが CRLF になり、行末の検査がコメントだけの変更でも不合格になるためである。
`--filters` の出力が作業ツリーと一致するのは、現在の設定でチェックアウトした作業ツリーに限る。
束の作業ツリーはこの条件を満たす。
既存のチェックアウトでは、担当外の変更と行末の検査を git の判定に寄せる。
担当外の変更は `git diff --name-only <base>` で判定し、行末は `--filters` の出力か blob のどちらかと一致すれば合格にする。
シンボリックリンクは、コミットと作業ツリーのどちらでも一覧から除く。コミットではリンク先のパスが、作業ツリーではリンク先の内容が読まれ、変更が無くても時点の間で食い違うためである。
作業ツリーの担当ファイルは、親ディレクトリまでにリンクがあれば読み込まず、終了コード 2 で停止する。
`node:child_process` を読み込むのは `src/snapshot/git.js` だけにする。
`check` のモジュールは `git.js` を静的に読み込まず、`--offline` でないときだけ動的に読み込む。
eslint の `no-restricted-imports` で、`src/check/` と `src/snapshot/fs.js` から `node:child_process` と `git.js` を読み込むことを禁じる。
`check --offline` は `--repo` の解決にも git を使えないので、`--repo`(既定はカレントディレクトリ)をそのまま作業ツリーのルートとする。

## 集計

`stats` の数え方は、移行元の `comment-stats.js` の `fileStats` にそろえる。rec-studio の過去の PR の表と比べられるようにするためである。

- 先頭の BOM を外し、CRLF を LF にそろえてから数える。行は `\n` で数え、末尾の改行の後は行に数えない。
- コメント行は、コメントの区間が空白以外の文字を持つ行である。コメント以外の区間の有無で、コメントだけの行と行末のコメントに分ける。
- コメント文字数は、コメントの区間から空白を除いたコードポイントの数で、`//` や `/*` などの記号を含む。
- doc コメントの行は、字句解析が doc コメントとした区間を持つ行である。区切り線の行は、言語の `separatorPattern` に当たる行である。どちらも、言語が持たなければ 0 とする。
- コード行は、コメント以外の区間(コードと文字列)が空白以外の文字を持つ行である。複数行の文字列の途中の行もコード行に数える。
- UTF-8 として読めないファイルは数えず、件数を警告に出す。

`stats` はファイルごとの値を JSON に書き、表にするときにまとめる。
設定に `areas` があれば領域でまとめ、無ければパスの第 1 階層(`src/`、`tests/` など)でまとめる。
対象は、設定の `scope` と `languages` が決める(設定ファイルの節)。
設定が無ければ、字句解析が言語を返すファイルから、`lint` と同じ既定の除外(`third_party` など)を除いたものとする。
どちらも `--paths <接頭辞>...` で絞れる。
`plan` の重みも同じ対象の決め方と数え方で求める。対象の決め方が食い違うと、束に入らないファイルが表に出るためである。
`stats --compare` は、時点ごとの JSON を 2 つ以上受け取り、領域ごとの表を Markdown で出す。

## 束の作り方

`plan` は、対象のファイルを次の順で束に分ける。

1. ファイルごとに重みを求める。重みは「コメント文字数 ÷ 50 + 3 行を超えるコメントのブロックの行数の合計」とする。移行元の実績では、コメント文字数と重みの比がおよそ 50 だった。値は基準コミットの読み取り口から、`stats` と同じ数え方で求める。UTF-8 として読めないファイルは束に入れず、一覧で知らせる。
2. 領域ごとに分け、領域をまたぐ束は作らない。
3. 領域の中で、同じディレクトリにある同じ語幹(拡張子を除いた名前)のファイルを 1 つの単位にする。宣言と定義(`.h` と `.cpp`、`.hpp` と `.inl` など)が同じ束に入る。
4. 単位をパスの順に並べ、1 束の重みが上限(`plan.maxWeight`、既定 700)を超える手前で区切る。同じディレクトリの単位は続けて並ぶので、同じ束に寄る。上限を超える 1 単位は単独の束にする。
5. 束ごとに、担当ファイルのコメントが参照している資料を集めて `docs` に書く。

束の名前は、回の名前の頭文字の大文字と 2 桁の連番(回 `volume` なら `V01`。100 束を超えたら 3 桁)とする。
重みのコメント行数は、行数の検査と同じく、空行と引数説明の除外を適用した行数である。重みは丸めずに保持する。
単位の並び順は、その単位の先頭ファイルのパスで決める。
設定した領域に当たらないファイルは、`stats` と同じ領域 `(なし)` にまとめる。
ファイルと領域を整列して扱い、同じ基準コミットと設定からは同じ束の定義を作る。
`plan` は解決した基準の SHA とコミットの日付を出す。`origin/main` は取得し直さないので、古いことに気付けるようにするためである。
重みが 0 のファイルが多い領域では 1 束のファイル数が膨らむが、ファイル数の上限は最初の試行で要るとわかってから足す。

既定の上限は、移行元の実績(34 束で、1 束 1〜41 ファイル、コメント 3,660〜102,505 字、重み 66〜1,616、中央値は 12 ファイル、31,678 字、重み 622)から決めた。
最初の試行で見直す。

## 実行者への委譲

### 起動と待ち合わせ

道具は実行者を起動しない。
グローバルの CLAUDE.md「モデル役割分担」は、実装の委譲を Agent ツールの窓口(`impl-*`)に限り、`codex-agent.sh` の直接起動を禁じている。
待ち方、終了コードごとの扱い、Claude 側への再委譲は窓口の定義にしか書かれていないので、道具が自前で持つと二重の実装になる。

`run` は束ごとに次を行う。

1. 基準コミットから束の作業ツリーを `.comment-tidy/worktrees/<回>/<束>` に作る。既にあれば再開として扱う。`--fresh` なら、途中の変更を捨てて作り直す。
2. 作ったばかりの作業ツリーから、担当ファイルの写しを `.comment-tidy/work/<回>/base/<束>/` に書き出す。あわせて、対象の範囲の全ファイルのハッシュの一覧を書く。
3. 依頼文を作り、`.comment-tidy/work/<回>/prompts/<束>.md` に書く。
4. `.comment-tidy/work/<回>/state/<束>.json` に「用意済み」と時刻を書いて戻る。

基準の写しを git の blob からではなく作業ツリーから取るのは、行末の変換(`text=auto` と `core.autocrlf`)で、blob と作業ツリーの行末が違うことがあるためである。
blob と比べると、行末の検査が常に不合格になる。

`run` は複数の束を受け、設定、細則、状態、置き場をすべて確認してから書き込みを始める。
通常の再開では、担当ファイルの基準の写しをハッシュと照合し、依頼文だけを更新する。
現在の設定で対象になる基準コミットの全ファイルが、保存済みのハッシュに含まれることも確認する。
設定変更や `--config` の差し替えで対象範囲が広がり、ハッシュが欠けた場合は再開を拒否して確認後の `--fresh` を求める。
既存の用意済み、報告あり、検査済みの状態は保持する。
基準の写しとハッシュは、再開した作業ツリーから取り直さない。
準備完了の記録がない作業ツリーや、欠けた準備は自動で補わず、確認後の `--fresh` を求める。
委譲中と取り込み済みの束は、`--fresh` を含めて拒否する。
作業ツリーは対象リポジトリに属する基準コミットの detached HEAD に限り、ブランチへ移ったものや HEAD が異なるものは削除しない。
`--fresh` は指定した束の作業ツリー、基準の写し、ハッシュ、依頼文、報告、検査結果、状態を作り直す。
保存が失敗した場合、途中の生成物が残ることがあるが、準備完了の状態は最後に保存する。
複数束の処理途中で失敗した場合、先に準備完了した束は保持する。

メインセッションは、束ごとに `delegate <束>` で「委譲中」を記録してから、Agent ツールの `impl-standard` を背景で起動し、依頼文の本文をそのまま渡す。
窓口が実行 ID(`run=` の行)を返したら、`delegate <束> --run-id <ID>` で記録する。
実行 ID は最初の委譲の呼び出しでも指定できる。
ID の追記と同じ ID の再記録は、委譲開始時刻と状態のほかの補足を保持する。
委譲中に別の ID へ置き換えることと、ID の指定なしで再び委譲することは拒否する。
ID は空白と制御文字を含まない文字列とし、`--cancel` との同時指定は拒否する。
委譲中の束は、`status` の次に渡せる束に出ない。
セッションを中断して再開したときは、`status` が出す実行 ID で `codex-agent.sh --wait <実行 ID>` を実行して、終わったかを確かめる。
実行 ID が記録される前に中断したときは、Agent ツールの状態を確かめ、渡していなければ `delegate <束> --cancel` で戻す。
窓口を止めても、起動済みのラッパーと Codex は止まらずに最後まで動く。
そのため、窓口が転送まで進んだかが分からなければ、ログの置き場(`~/.claude/codex-agent/logs`)で、委譲の記録より後に始まった同じ窓口の実行を探す。
候補を `--wait` で待ち、監査行の `prompt-file=` が指す依頼文がその束の作業ディレクトリを含み、ハッシュが一致することを確かめてから `--run-id` で記録する。
候補が無ければ渡していないものとして取消する。
取消は委譲中の束だけに使い、状態の実行 ID、報告、検査結果、記録を初期化して「用意済み」に戻す。
作業ツリーと基準の写しは変更しない。
実行者の停止は行わないので、実行済みなら停止を確認してから取消する。
窓口の完了の通知を受けたら、報告の `run=` の実行 ID で `codex-agent.sh --wait <実行 ID>` を実行し、その標準出力をファイルに保存して `report <束> <ファイル>` で取り込む(claude-codex-bridge の docs/gpt-agents.md「完了の報告を取り出す」)。
`report` は保存した報告を `.comment-tidy/work/<回>/reports/<束>.md` に写し、状態を「報告あり」にする。
委譲中の束だけに実行し、入力の相対パスは呼び出したディレクトリを基準とする。
報告は UTF-8 として解析し、保存するバイト列は BOM と行末も含めて元のまま保持する。
報告の実行 ID は、最初の欄が `run=` の監査行(`codex-agent: run=<ID> pid=...`)からだけ取る。
`warning=concurrent-writer` の行の `run=` は相手の実行 ID であり、自分の ID として扱わない。
その実行 ID が委譲の実行 ID と異なる場合、または複数の実行 ID がある場合は保存前に拒否する。
実行 ID が監査行にない場合や委譲時に未記録の場合は、ID の一致を検証せず報告を取り込む。
監査行(`codex-agent: agent=`)と `result=` の行が無ければ、状態に「監査行なし」を記録する。
`warning=child-spawn-failed` か `warning=sandbox-build-failed` の行があれば、実行者の検証は済んでいないものとして扱い、メインセッションが `check` を実行し直す。
これらの警告と `ok` 以外の実行結果は、状態の `notes` に記録する。
`warning=concurrent-writer` の行は、相手の実行 ID を添えて `notes` に記録する。
窓口の作業場所はセッションの作業ディレクトリなので、束の作業ツリーが別でも並行に渡せば出る。
束の作業ツリーが重なったかは、監査で差分の出所を確かめて判断する。
報告の解析と候補の検証後に報告のファイルを保存し、その後で状態を保存する。
状態の保存に失敗した場合は報告のファイルが残ることがあるが、委譲中の状態を保つので同じ報告を再取り込みできる。

1 つの作業ツリーに同時に書き込む担当は 1 つに限る(同資料「既知の制約」)。
束ごとに作業ツリーを分けるのはこのためで、実行中の束の作業ツリーはメインセッションも編集しない。
道具は実行者のプロセスを見ないので、委譲中かどうかは `delegate` と `report` の記録だけで決まる。
メインセッションは、委譲中の束を `delegate --cancel` か `report` で解く前に、同じ束を再び渡さない。

3 つの窓口(`impl-light`、`impl-standard`、`impl-hard`)は同じ実装用のアカウントを使うので、利用上限はすべての束で共有される。
同時に渡す束の数は `implementer.parallel`(既定 2)を目安にし、最初の試行で見直す。
ほぼ同時に起動すると作業ツリーの重なりの警告が出ないことがあるので、起動は 1 本ずつ間を空ける。

窓口が利用上限などで Claude 側への再委譲を報告したときは、同資料「再委譲の流れ」に従う。
Claude 側へ回してよいのは、アカウント自体が使えないときだけである。
回すときは、途中までの変更が残る作業ツリーを `run --fresh` で作り直してから渡す。
実行者が混ざると、監査で変更の出所を見分けられなくなるためである。
Codex の利用上限の解除を待って、同じ実行者で再開するときは作り直さない。
上限の報告では Codex が起動していないので、作業ツリーに変更が無いことを確かめて `delegate --cancel` で戻し、同じ依頼文を渡し直す。
上限の報告を `report` で取り込むと、取消できない「報告あり」へ進むので取り込まない。

`check`、`audit`、`apply` は実行者に依存しない。

### 依頼文

依頼文は次の見出しで構成する。

1. 位置づけ(新規か再開か。再開なら担当ファイルを「変更あり」と「未着手」に分けて示す)
2. 目的
3. 落とさないもの
4. 作業ディレクトリ
5. 必ず読むもの(`rulesPaths` のコメント記述ルールの正本、判定基準の細則、束の `docs`)
6. 担当ファイルの状態(3 行を超えるブロックの行範囲つき)
7. 禁止事項
8. 検証(`check --offline` の実行を含む)
9. 報告(末尾の JSON を含む)

束の作業ツリーが無ければ新規、あれば再開とする。
`prompt` は依頼文を標準出力へ出すだけで、作業ツリーや状態を作成、更新しない。
再開のときの「変更あり」は、作業ツリーで担当ファイルに絞った `git status --porcelain` から決める。
担当ファイルの状態は、作業ツリーがあればそこから、無ければ基準コミットの読み取り口から取る。

目的と落とさないものと禁止事項の可変部は、判定基準の細則の決まった見出し(`## 目的`、`## 落とさないもの`、`## 対象外`)から埋め込む。
落とさないものには、道具の既定として次を持つ。
ライセンス表示、移植の約束、テストの入力値の根拠、契約の語(主語、順序、条件を変えない)、共通規約の正本の適用範囲である。
実行者が要約で落としやすいものなので、細則に書かなくても必ず入れる。

依頼文には、git の語(`GitHub`、`.gitignore` のように git を含む語も含む)、コミットや push の指示、実行者の選び方についての自由文を書かない(グローバルの CLAUDE.md「モデル役割分担」)。
細則から埋め込む文にこれらが含まれていれば、`prompt` と `run` は依頼文を出さずに、該当する行を示して止まる。
検査は細則から埋め込んだ文にだけ当てる。道具の定型文(作業ディレクトリのパスなど)に禁止の語が無いことは、道具のテストで守る。
依頼文に書くパスの形は 1 つの関数で決める。Codex のサンドボックスで通る形は段階 4 の試行で確かめる。
`rulesPaths`、`docs`、中央の道具の `bin/comment-tidy.js` は作業ツリーの外にあるが、Codex のサンドボックスは作業ツリーの外を読めるので、絶対パスで示す。
`prompt` は正本を案内するため、空でない `rulesPaths` を必要とする。
`check --offline` のコマンドは、現在の入口が受け付ける `--repo`、`--base-dir`、`--hashes`、`--config`、`--files` を明示する。
Windows では PowerShell、それ以外では POSIX のシェルの引数の引用を使う。

### 報告の JSON

窓口の定義は、実行者の最終報告を 3 つの見出し(判断が必要なこと、やったこと、未対応の問題)で書かせる。
依頼文はこれに重ねて、「やったこと」の最後に、機械で読める JSON のブロックを 1 つ置かせる。
含めるのは実行者の判断だけで、差分から機械で分かるもの(変更したファイル、丸ごと消したブロック)は含めない。

```json
{
  "docsCandidates": [{ "file": "src/project/SavePolicy.h", "lines": "65-74", "summary": "..." }],
  "needsDecision": [{ "file": "src/project/ProjectSettings.h", "lines": "90-91", "summary": "..." }],
  "codeImprovements": [{ "file": "src/project/RangeEdit.cpp", "lines": "215-359", "summary": "..." }]
}
```

`lines` は基準コミットの行番号とする。
`report` は、報告の本文(`codex-agent:` で始まる行を除いた部分)の最後の JSON のブロックを読み、無ければ束の状態に「報告の JSON なし」を記録する(不合格にはしない)。
JSON のブロックは Markdown のコードフェンスの言語名 `json` で判定し、ほかのコードフェンスの内部は読まない。
最後の JSON が閉じられていない場合、解析できない場合、三つの候補の配列がない場合は、報告と状態を変更せず終了コード 2 で止める。
候補の `file` は束の担当ファイルの相対パス、`lines` は正の行番号または昇順の範囲、`summary` は空でない文字列とする。
行番号は基準コミットのファイルの行数以内でなければならない。
`status` と `audit` はこの JSON を集め、資料へ移す候補、判断が要る事項、コード改善の候補を、束をまたいで一覧にする。

## 検査

`check` は、束の作業ツリーについて次を確かめ、1 つでも満たさなければ不合格にする。

| 検査 | 内容 |
|---|---|
| 字句の同一性 | 担当ファイルのコメント以外のトークンと文字列リテラルが基準と同じ |
| 担当外の変更 | 担当ファイル以外に変更が無い。Git 経由では `git diff --name-only <base>` で判定し、未追跡ファイルは検出しない。`--offline` ではハッシュ一覧と比べる |
| コメントの行数 | 1 か所のコメントが上限(既定 3 行)を超えない |
| 行末 | 変更したファイルの行末の種類(LF、CRLF、混在)、末尾の改行の有無、BOM の有無が基準と同じ。Git 経由では `--filters` の出力か blob のどちらかと同じなら合格 |

字句の同一性は、前後のファイルの `normalizedCode` が等しいことで判定する。
正規化したトークン列は空白を持たないので、コメントを消して行が詰まることや、行末のコメントを消して末尾の空白が残ることは差にならない。
空白だけの変更はこの検査では見ず、監査で見る。
差があれば、最初に食い違うトークンの、前後それぞれの行番号と周りのトークンを結果に書く。
担当ファイルが作業ツリーから消えていれば不合格、字句解析の言語が無いファイルが担当にあれば引数の誤り(終了コード 2)とする。

行末を行ごとに比べないのは、コメントの行を消しただけで差になるためである。

担当外の変更は、Git 経由では `git diff --name-only <base>` に含まれる担当外のパスで判定する。
git の正規化に従うため、未追跡ファイルはこの判定に含まれない。
`--offline` では、ハッシュ一覧にあるファイルのハッシュが変わったか、ファイルが消えたことで判定する。
ハッシュ一覧に無い新しいファイルは、対象の範囲(`scope`)を読める段階 2 まで検出しない。
ハッシュの一覧は `{ "algorithm": "sha256", "files": { "<相対パス>": "<16 進>" } }` の形で、読み書きを `src/snapshot/hash-list.js` に置く。

コメントの行数の数え方は、`lint` の `length` と同じ関数を使う。数え方を 2 か所に持つと、片方だけが直ってずれるためである。

「1 か所」は、コメントだけの行が連続する範囲とし、全言語に同じ規則を当てる。
コードと同じ行に収まるコメントは、その 1 行だけを 1 か所とする。
複数行にわたるコメントは、始まる行や閉じる行にコードが並んでいても、その行を含めて 1 か所とする(最初や最後の行だけをコードと並べて上限を逃れる書き方を、数え漏らさないため)。コードが並ぶ行で 1 か所は切れるので、始まる行より前と、閉じる行より後ろのコメントだけの行とはつなげない。
空行で区切って上限を逃れる書き方は、監査で見る。
`@param` などの注記の行と、`licensePatterns` に当たるブロックは数えない。

次の検査は警告にとどめ、不合格にはしない。

| 検査 | 内容 |
|---|---|
| 行の幅 | 足したコメントの行が上限の幅(既定 108 桁)を超える。Unicode の East Asian Width が F と W の文字を 2 桁と数える。範囲の表は依存を持たないために自前で持ち、Unicode の EastAsianWidth.txt から作るスクリプトを `tools/` に置く |
| 資料の参照 | 足したコメントの資料の参照が、実在する見出しを指す(`refs` と同じ規則) |

`check --offline` は、実行者のサンドボックスから呼ばれる。
git を含め子プロセスを起動せず、作業ツリーの外へ書き込まず、結果は標準出力だけに出す。
Codex が書き込めるのは作業ツリーの中だけで、基準の写しのある `.comment-tidy/work/` は読めるが書けない。
作業ツリーの基準コミットが `init` より前で、作業ツリーに設定ファイルが無いことがあるので、`--config <絶対パス>` で設定を渡せるようにする。

束を取らず、比較元と担当ファイルを明示する `check` は、次の 2 つの形で呼び出す。

```text
comment-tidy check --base <コミット> --files <パス...> [--config <パス>] [--out <ファイル>]
comment-tidy check --offline --base-dir <写し> --hashes <ハッシュの一覧> --files <パス...> [--config <パス>]
```

`--base-dir` は `.comment-tidy/work/<回>/base/<束>/` を指し、その下に担当ファイルが相対パスのまま並ぶ。
この形では位置引数を併用せず、`--files` が無ければ引数の誤りとする。
CLI は引数を `runCheck({ files, baseline, target, hashList, config, offline })` の形へ変え、束を取る `check` も束の定義から同じ形を作る。

結果の形は次のとおりである。
検査の名前の文字列は `src/check/` のモジュールが書き出し、`status` と `audit` はそれを使って、文字列を書き直さない。

```json
{
  "schemaVersion": 1,
  "pass": null,
  "batch": null,
  "base": "<コミットか null>",
  "baseDir": "<写しのディレクトリか null>",
  "offline": false,
  "checkedAt": "2026-10-04T00:00:00Z",
  "files": ["src/a.cpp"],
  "ok": false,
  "failures": [{ "check": "token-identity", "file": "src/a.cpp", "line": 12, "detail": "..." }],
  "warnings": [{ "check": "line-width", "file": "src/a.cpp", "line": 30, "detail": "..." }],
  "summary": { "token-identity": 1, "line-width": 1 }
}
```

検査の名前は `token-identity`、`out-of-scope-change`、`comment-lines`、`line-ending`、`line-width`、`doc-ref` とする。
束を取らない通常の検査は `--out` があればそこへ書き、無ければ標準出力に要約を出す。
束を取る通常の検査は `.comment-tidy/work/<回>/check-<束>.json` へ書き、結果の `pass` と `batch` には回と束の名前を入れる。
`--offline` はどちらの形でも結果を保存せず、標準出力に要約を出す。

## 監査

`audit` は、削った hunk と足した hunk から、人が読むべき箇所を拾う。

### 重要語の消失と、それ以外の既定の検査

- 重要語の消失: 削った文にあって、足した文にも、同じファイルの他の箇所にも、参照先の資料にも無い語。語は群(スレッドと寿命と順序、数値と単位、互換、撤去条件)に分け、既定の語に設定の `audit.keywordGroups` を足す。外部 API の語はプロジェクトごとに違うので、既定には持たない。
- 4 行以上の丸ごと削除: 足した文が無い削除。
- 逃げ言葉: 足した文の「など」「適宜」「必要に応じて」「適切に」。
- 実在しない参照: 足した文の資料の参照が、実在する見出しを指さない。

### 誤りの型の検査

実行者の出力に現れやすい、次の誤りの型を拾う。

| 検査 | 例 |
|---|---|
| 未決と仮決めの消失 | 削った文の「仮決め」「未決」「TODO」「判断事項」が、足した文に無い。決定済みのように読める文になる |
| 括弧の対応 | 足した文で、括弧が閉じないまま次の文が続く |
| 同じ行の重複 | 同じ文の行が、1 つのファイルの複数の箇所に足された |
| 元に無い語 | 足した文に、削った文にも参照先の資料にも無い語(名詞)がある |
| 自己参照 | ファイルの冒頭に、そのファイル自身を指す文(「このファイルのテストで固定する」)が足された |
| 近くの宣言への混入 | ある宣言の説明にあった語が、隣の宣言のコメントへ移った |

「元に無い語」と「近くの宣言への混入」は誤検出が多くなりうるので、監査の材料に並べるだけにする。

### 監査の材料

`audit` は `.comment-tidy/work/<回>/audit-<束>.md` に、検査ごとに該当する hunk を、削った文と足した文を並べて書く。
あわせて、束の削減率と、報告の JSON から拾った候補を書く。
メインセッションはこの材料を読み、どこにも残っていない規則を 1 行で戻してから `apply` する。

## 取り込み

`apply` は、次をすべて満たすときだけ、束の担当ファイルを統合先へ写す。

- 束の `check` が合格している。
- 統合先が main ではないブランチにいて、基準コミットがそのブランチの祖先である。
- 統合先の HEAD の担当ファイルが、基準コミットの担当ファイルと同じである(別の束や監査の修正を上書きしないため)。
- 統合先の担当ファイルに、未コミットの変更が無い。

`apply <束> [--pass <回>] [--repo <統合先>] [--config <絶対パス>]` で実行する。
状態が `checked` で、状態の最新の `check` が同じ回、束、基準の通常検査に合格していることを確認する。
不合格で `check.ok` が `false` の場合や、保存失敗で `check` が `null` の場合は取り込まない。
担当ファイルは HEAD の内容とモード、作業中のバイト列、インデックスの変更を確認し、祖先関係や置き場が不正な場合も書き込み前に拒否する。
担当外のコミットや未コミットの変更は許す。

束を再検査し、最新の結果を保存する。
再検査が不合格なら担当ファイルは書き換えない。
合格なら検査で読んだバイト列を担当ファイルにだけ写し、内容、行末、既存のファイルモードを保つ。
すべての書き込み後に `applied` を記録する。
書き込みや状態保存に失敗した場合は書き込んだ担当ファイルを元のバイト列へ戻し、復元に失敗したファイルをエラーに含める。
プロセスの強制終了や OS の停止をまたぐ複数ファイルの原子的な取り込みは保証しない。
その場合は統合先の差分を確認して復元し、再検査してから取り込む。

コミットはメインセッションが差分を確認して行う。
`--commit` は受け付けない。
取り込みの記録は `state/<束>.json` に書き、`clean` と `status` が使う。

## 非公開の宣言の doc コメントの置き換え

`privatize` は、判定基準が非公開と定める宣言に付いた doc コメントの記号を、通常のコメントの記号へ置き換える。
回のすべての束を取り込んだ後に 1 回だけ実行し、生成物だけの 1 コミットにする。
束の差分と行が重なるので、束の PR を先にマージし、その後の main で作る。

最初に対応するのは C++ で、置き換える範囲は次のとおりである。

- 設定の `privatize.cpp.implementationFiles` と `testFiles` に当たるファイルのすべて。
- ヘッダーの private と protected の区画(class の既定の private と、非公開の区画の中の入れ子の型を含む)。
- 無名名前空間と `detail` 名前空間の中。
- 関数本体、ラムダ、初期化子の波括弧の中。

区画の判定は、コードの波括弧とアクセス指定ラベルから行う。
構造の検査(ファイル末尾で波括弧の深さが 0、アクセス指定ラベルが class の区画の外に無い、template 頭が閉じている、ヘッダーの公開の区画で型の本体か関数本体かを決められない波括弧が無い)に 1 件でも失敗したら、何も書き換えない。
`///` は 1 文字、行末の `///<` は 2 文字を削るだけで、本文、行末、BOM は変えない。

`--report` は、置き換える行の一覧(種類と直近のアクセスラベル)と、残す doc コメントの直後のコード行の先頭語の集計を出す。
`--verify` は、置き換えた後の差分の各行が記号だけの違いで、ファイルごとの追加と削除の行数が同じであることを確かめる。

## PR の切り出しと本文の表

回の差分は大きく、1 本の PR では相互レビューの差分の上限を超える。
`branch <領域>` は、統合先から領域のファイルの差分だけを取り出し、main から切ったブランチ(`comment-tidy/<回>-<領域>`)に 1 コミットで載せる。
領域ごとのブランチは触るファイルが重ならないので、どの順でマージしてもよい。
それでも 1 本が相互レビューの上限を超えるときは、`--max-diff-kb` で差分の上限を引き上げ、`--max-file-diff-kb 0` でファイルごとの要約への置き換えを止めて、全文を渡す。
ai-cross-review は、既定では 64KB を超えるファイルの差分を要約に置き換え、全体が上限を超えると黙って要約へ縮退するので、コメントの本文をレビューできなくなる。

PR の本文は /github-writing の項目に従い、`table` の表は「変更内容」に置く。

`table` は、指定したファイルの範囲と、リポジトリ全体の 2 つの表を作る。
列は「対応前」と、回ごとに 1 列(「1 回目」「2 回目」)とする。
1 つの回を複数の PR に分けても、PR ごとの列には分けない。
その PR までの、その回の整理をすべて含めた値を 1 列に入れる。

各列の時点は次のとおりである。

| 列 | 時点 |
|---|---|
| 対応前 | 最初の回の `batches-<回>.json` の `base` |
| N 回目 | N+1 回目の `base`。次の回が無ければ、作業ツリーまたは `--head` で指定したコミット |

行は、コメント行、コメント文字数、doc コメントの行、区切り線の行、コード行とする。

## 資料の参照の検査

`refs` は、対象の範囲のコメントと資料から、設定の `docs.refPattern` に当たる参照を探し、参照先の資料に同じ見出しがあるかを確かめる。
見出しの一致は、括弧書きの補足を除いた前方一致を許す(例: 「参照実装とのクロスチェック」は「参照実装とのクロスチェック(段階 5)」に当たる)。
資料の見出しを変えたときに、参照の直し漏れを見つけるのに使う。

## 編集時とコミット前の検査

`lint` は、コメント記述ルールのうち機械で判定できる規則を、コメントを書いた直後とコミットの直前に検査する。
整理の回とは独立して動き、回が終わった後も使い続ける。
規則を文章として読ませるだけでは、破られても誰も気付けないためである。

### 入口

| 入口 | 起動 | 比べるもの |
|---|---|---|
| `lint --hook post-edit` | Claude Code の `PostToolUse`(Edit、Write)。標準入力のフックの JSON から、ファイルと編集の内容を読む | 作業ツリーのファイルと HEAD |
| `lint --hook pre-commit` | Claude Code の `PreToolUse`(Bash、PowerShell)。コマンドが `git commit` のときだけ動く | コミットに含まれる範囲に応じて検査する(下表) |
| `lint <ファイル...>` | 手で実行する | 作業ツリーのファイルと HEAD |
| `lint --changed` | 手で、または実行者の検証から実行する。HEAD から変わったファイルと、未追跡のファイルを調べる | 作業ツリーと HEAD |
| `lint --staged` | 手で実行する | インデックスと HEAD |

フックを 2 つに分けるのは、実装の多くが Codex への委譲で行われ、その編集が Claude Code のフックを通らないためである。
コミットはメインセッションが行うので、コミット前の検査は両方の経路の変更を拾う。

Claude Code はフックの JSON を標準入力へ渡す。
`cwd` が無ければプロセスの作業フォルダーを使う。
`PostToolUse` は `Edit` と `Write` だけを扱い、`PreToolUse` は `Bash` と `PowerShell` だけを扱う。
イベント、ツール、必要な入力項目の型が合わないときは、何もせず終了コード 0 を返す。
標準入力が端末につながっているときは読み取りを待たない。

`post-edit` は `tool_input.file_path` のファイルを含むリポジトリを探し、ファイル全体の新しい違反を調べてから編集範囲に重なるものだけを残す。
`tool_response.structuredPatch` が配列なら、各要素の `newStart` から `newStart + newLines - 1` までを範囲とし、`newLines` が 0 のときは `newStart` の 1 行を使う。
この範囲は `Edit` と、`tool_response.type` が `update` の `Write` で使う。
`structuredPatch` が無い `Edit` は、ファイルと `new_string` の行末を LF にそろえて検索し、`replace_all` が真なら一致したすべての範囲を使う。
`replace_all` が偽なら最初の一致だけを使う。
`new_string` が空か見つからないときは範囲を作らず、何も報告しない。
`structuredPatch` が無い `Write` はファイル全体を範囲とする。
対応言語でないファイル、存在しないファイル、リポジトリ外のファイルは何もせず通す。

`pre-commit` は `tool_input.command` の各コマンドを調べ、Git のグローバルオプションの後にサブコマンド `commit` があるときだけ検査する。
引数に `commit` を含むだけのコマンドや `commit-tree` のような別のサブコマンドは対象にしない。

| コマンドの形 | 検査する範囲 |
|---|---|
| `git commit <path...>`(`-i` / `--include` なし) | 指定パスに絞った `changed`。未追跡は含めない |
| `git commit -i <path...>` / `--include` | `staged-with-worktree`。指定パスは作業ツリー、範囲外はインデックスを調べる |
| 前に `git add <path...>` | `staged-with-worktree`。指定パスでは未追跡も含める |
| 前に `git add -A` / `--all`、ルートの `.`、またはワイルドカードか `:` で始まるパス | 未追跡を含む `changed` |
| `git commit` にワイルドカードか `:` で始まるパス | 未追跡を除いた `changed` |
| 前に `git add -u` / `--update`、または `git commit -a` / `--all` | 未追跡を除いた `changed` |
| `git commit` の引数を解釈できない | commit のパスと `-a` を無いものとして先行する `git add` を判定する。該当しなければ `staged` |
| ほかの形 | `staged` |

`changed` は作業ツリーと HEAD、`staged` はインデックスと HEAD、`files` は作業ツリーと HEAD を比べる。
`staged-with-worktree` は、指定パスの範囲では作業ツリーと HEAD を比べ、範囲外ではインデックスと HEAD を比べる。
指定範囲のファイルは作業ツリーの内容を使い、インデックスの内容は使わない。
フックはシェルが展開する前のコマンドを受けるので、ワイルドカードを含むパスからは範囲を推定しない。
変更の一覧は絞らずに取ってから範囲で絞る。範囲の外にあった元のファイルからの名前の変更を見失わないためである。
`changed` から未追跡を除く指定は `git commit -a`、`git commit <path...>`、`git add -u` に限り、通常の `lint --changed` は未追跡も含める。
指定パスは `git add` または `git commit` を実行する位置から解決し、実体のパスをリポジトリルートからの相対パスに直して pathspec に渡す。
ルートの外を指すパスがあれば `staged` を調べる。
先頭の `cd`、`Set-Location`、`sl`、`pushd` は順に適用し、相対パスは直前の位置を基準に解決する。
先頭の `(` と `NAME=value` の形の環境変数指定は読み飛ばす。
Git のグローバルオプションでは `-P` も受け付ける。
ヒアドキュメントの本文は、区切りの行までコマンドとして扱わない。
リポジトリ外のコマンドは何もせず通す。

### 報告するもの

報告するのは、比べる元(HEAD)に無かった違反だけである。
既存の違反まで報告すると、変更と関係のない既存コメントを同じ差分で整理させることになり、コメント記述ルール「既存コメントの扱い」に反する。

違反が同じかどうかは、規則の ID と、コメントのブロックの本文(空白を詰めたもの)の組で決める。
位置が動いただけのコメントは、新しい違反にしない。
比べる元に無いファイルは、すべての違反を報告する。

`post-edit` は、さらに今回の編集が触れた行の範囲に重なるブロックだけを報告する。
同じファイルを続けて編集するたびに、前の編集の違反を繰り返し報告しないためである。
ここで報告しなかった違反は、コミット前の検査が拾う。

### 規則

| ID | 内容 | 扱い |
|---|---|---|
| `length` | 1 か所のコメントが上限(`maxCommentLines`、既定 3 行)を超える。数え方は `check` の「コメントの行数」と同じ | 確定 |
| `issue-ref` | Issue や PR の番号。同じブロックに TODO、FIXME、HACK、`Tracking`、「追跡先」のどれかがあれば、追跡先を示す番号とみなして除く | 確定 |
| `date` | 日付。ただし、直前が `/` または `\`、直後が英字で始まる拡張子、同じ行の「」内にある日付を除く | 確定 |
| `separator` | 区切り線や囲みの罫線(字句解析の `separatorPattern`)。C++、C#、JavaScript では、スラッシュだけが 4 つ以上並ぶ行も含む | 確定 |
| `history` | 経緯の語(「以前は」「従来は」「当初」など。「以前の」「最初は」「リリース前」は除く) | 見直し候補 |
| `change-log` | 変更の記録(「修正した」「変更した」「追加した」など)。動詞は、文末、丸括弧の閉じの前、「ので」「ため」の前にあるときだけ当てる。複数行のコメントの途中の行末は、折り返しと区別できないので文末とみなさない | 見直し候補 |
| `work-note` | 作業の意図、段階のラベル、手順の番号、レビューや指摘の出所(「今回の対応」「フェーズ 2」「ステップ 3」「レビュー指摘」など)。段階のラベルは、同じ行の「」の中と、`docs/` で始まるパスの直後を除く | 見直し候補 |
| `todo-no-ticket` | TODO、FIXME、HACK があり、同じブロックにチケットの番号(`ABC-123` の形、`#123` の形、URL、`Tracking`、「追跡先」)が無い | 見直し候補 |

確定は、語や形だけで違反と決まるものである。
見直し候補は、語が当たっても違反とは限らないため、書き手が読み直して判断する。
語の一覧は移行元の `residue2.js` を基にし、実行時の状態の説明(「動作中だった」「参照していたパス」「追加したトラック」)と資料の節への参照には当たらないようにしている。

次のものは対象から外す。

- `licensePatterns` に当たるブロック
- ツールが解釈する注記(警告の抑制、整形の切り替え、生成物の印)。既定では `eslint-`、`NOLINT`、`clang-format`、`clang-tidy`、`@ts-`、`prettier-ignore`、`istanbul ignore`、`c8 ignore`、`cspell:`、`noqa` を含む行を注記とみなす。全部の行が注記のブロックを対象から外し、注記の行は `length` の行数にも数えない
- `scope.exclude` のパスと、git が無視するファイル

コードの中に抑制の印を書く仕組みは持たない。
誤って当たる語は、理由とともに設定の `lint.allow` へ足す。
`issue-ref` は、数字だけの 3 桁か 4 桁の色の値(`#333` など)も番号として当てる。番号と見分けられないためで、色を書くリポジトリでは `lint.allow` で外す。
`todo-no-ticket` のチケットの番号は、大文字 2 文字以上のキーに数字が続く形とし、同じ形の代表的な規格名(`UTF-8`、`SHA-256` など。一覧はコードにある)は番号とみなさない。

手で実行するときに `--repo` を省くと、カレントディレクトリを含むリポジトリのルートを使い、相対パスのファイル名はカレントディレクトリから解決する。
`--repo` を渡したときは、相対パスのファイル名をそのルートから解決する。
名前を変えたファイルは、変更前の名前の内容と比べる。
ステージしていない名前の変更は「削除と、未追跡の追加」に見えて組を作れないので、`changed` では、新しいファイルを、作業ツリーから消えたファイル全部の違反と比べる。
`scope.exclude` のパターンがフォルダーに当たるときは、その下のファイルにも当たる。

### 結果の返し方

| 入口 | 確定の違反がある | 見直し候補だけ | 違反なし | 検査の失敗 |
|---|---|---|---|---|
| `post-edit` | 報告を標準エラーへ出して 2 | 報告を標準エラーへ出して 2 | 何も出さず 0 | 標準エラーへ 1 行出して 0 |
| `pre-commit` | 報告を標準エラーへ出して 2。コミットを止める | 下記の JSON を標準出力へ出して 0。コミットは通す | 何も出さず 0 | 標準エラーへ 1 行出して 0 |
| 手での実行 | 一覧を出して 1 | 一覧を出して 0 | 0 | 標準エラーへ 1 行出して 2 |

フックの入口は例外を内部で受ける。
標準入力の JSON を読めない場合や、Git、字句解析、検査で失敗した場合も、1 行のエラーを標準エラーへ出して終了コード 0 を返す。
この扱いにより、検査の不具合では編集もコミットも止まらない。

`post-edit` の報告には、次の行を先頭に置く。

```text
comment-tidy: いま書いたコメントが、コメント記述ルールから外れています。
```

`pre-commit` で確定の違反を報告するときは、次の行を先頭に置く。

```text
comment-tidy: コミットに含まれるコメントに、確定の違反があります。直してからコミットしてください。
```

見直し候補だけの場合は、次の JSON を標準出力へ出す。
`additionalContext` は見直し候補の案内行と `formatReport` の文字列を改行でつないだ値である。

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "additionalContext": "comment-tidy: コミットに含まれるコメントに、見直し候補があります。\n<formatReport の文字列>"
  }
}
```

報告の 1 件には、ファイル、行、規則の ID、扱い、当たった語、直し方の 1 文を含める。
フックの入出力の形は Claude Code の版で変わりうるので、実装の時点で公式の資料を確かめる。

検査そのものの失敗(字句解析の例外、git の失敗、フックの JSON を読めない)では、編集もコミットも止めない。
道具の不具合で作業が止まると、フックごと外されて検査が働かなくなるためである。
失敗は標準エラーへ 1 行だけ出す。

### 設定の無いリポジトリ

フックはグローバルの設定に登録するので、`.comment-tidy/config.json` の無いリポジトリでも動く。
そのときは既定値を使う。

- 言語は拡張子で決める。対応する言語でないファイルは、何も出さずに通す。
- `third_party`、`node_modules`、`vendor`、`build`、`dist` の下と、git が無視するファイルは調べない。
- 上限の行数と `licensePatterns` は、設定ファイルの既定と同じ値を使う。

リポジトリごとに止めるときと、誤って当たる語を外すときは、設定に次の項目を書く。

```json
{
  "lint": {
    "enabled": true,
    "allow": [{ "pattern": "前回の保存", "reason": "実行時の状態を指す語" }]
  }
}
```

### フックの登録

`comment-tidy install-hooks [--settings <path>] [--dry-run] [--remove]` が Claude Code の設定にフックを登録する。
`--settings` の既定値は `~/.claude/settings.json` である。
登録するフックは次の 2 つで、コマンドには Node.js 実行ファイルと `bin/comment-tidy.js` の絶対パスを二重引用符で囲んで指定し、`timeout` を 30 秒にする。

| イベント | `matcher` | コマンドの末尾 |
|---|---|---|
| `PostToolUse` | `Edit|Write` | `lint --hook post-edit` |
| `PreToolUse` | `Bash|PowerShell` | `lint --hook pre-commit` |

既存の設定項目と別のフックは順序を保って残す。
この道具のフックがすでにあればコマンドと `timeout` を現在の値へそろえ、複数あれば 1 つにまとめる。
設定ファイルがシンボリックリンクなら、読み込み、控え、一時ファイル、置き換えには `fs.realpathSync` で得た実体のパスを使う。
読み込み時には先頭の UTF-8 BOM を取り除いてから JSON として読む。
内容が変わるときは、同じフォルダーに `settings.json.bak-<YYYYMMDD-HHMMSS>` の控えを作り、同じフォルダーの一時ファイルから設定を置き換える。
設定ファイルが無ければ `hooks` だけを持つファイルを新しく作り、控えは作らない。
`--dry-run` は変更予定と設定内容を表示し、ファイルへ書き込まない。
フックのコマンドには Node.js の絶対パスを記録するため、Node.js を入れ替えた後は `install-hooks` を実行し直す。
`--remove` はこの道具のフックだけを外し、そのフックを取り除いて空になったグループとイベントの配列を削除する。
元から空だったグループとイベントの配列は残す。
変更が無いときは控えを作らず、設定ファイルも書き込まない。
JSON を読めない設定は書き換えず、理由を標準エラーへ出して 2 で終わる。

Codex の実行者は、検証の手順の中で `lint --changed` を呼ぶ。
呼び出しを実行者の定義(`~/.claude/gpt-agents/` の `impl-*`)へ足すかどうかは、フックの運用を確かめてから決める。

## 束の作業ツリーの片付け

`clean [<束...>] [--pass <回>] [--repo <dir>] [--config <絶対パス>] [--dry-run] [--force]` は、道具が用意した束の作業ツリーとその Git の登録だけを片付ける。
回の選び方は束を取る既存のコマンドと同じである。
束を省くと、その回の状態が `applied` の束だけを選ぶ。
`--force` を付けても、束を省いたときの対象は増やさない。
`--dry-run` は通常実行と同じ確認を行い、対象の絶対パス、状態、解除するリンク、拒否理由を表示するだけで、ファイルや Git の登録を変えない。

状態の `applied` と取り込みの時刻を、取り込み済みの記録として使う。
状態と束の定義、基準の写し、ハッシュ、依頼文、報告、検査結果は残し、`cleaned` のような新しい状態は足さない。
未着手や状態のないディレクトリは道具が用意したものと確認できないため、削除しない。
明示した `prepared`、`reported`、`checked` の束に限り、`--force` で未取り込みの確認を外せる。
`delegated` は `--force` でも拒否する。
道具は実行者の停止を確認しないので、停止を確認してからメインセッションが `delegate --cancel` または `report` で委譲中を解く。

削除対象は、選んだ束の定義から決まる `.comment-tidy/worktrees/<回>/<束>` に限る。
管理用ディレクトリの各親と作業ツリーのルートにリンクがないこと、実際の絶対パスが対象リポジトリの管理用ディレクトリ内にあることを確認する。
作業ツリーが対象リポジトリに登録され、基準コミットの detached HEAD であることも確認する。
別リポジトリの作業ツリー、ブランチへ移った作業ツリー、HEAD が異なる作業ツリー、ロックされた登録、サブモジュールや入れ子のリポジトリは拒否する。
追跡ファイルのステージ済みと未ステージの差分は担当ファイルだけに限り、担当外の未追跡ファイルも拒否する。
Git が無視する未追跡ファイルも、削除すれば失われるので同じ確認に含める。
ファイルの追加、削除、名前の変更、モードの変更もパス単位で判定する。
担当外の通常ファイルは基準の内容と実際のバイト列も照合し、`assume-unchanged` で Git の表示から隠れた変更も拒否する。
`core.symlinks=false` で通常のファイルとして置かれた追跡リンクは、保存されたリンク文字列と照合する。
これらの確認は `--force` でも外さない。

選んだ束の確認を全件終えてから、束ごとに削除する。
引数や確認の失敗では一件も削除せず、終了コード 2 を返す。
削除途中の失敗は復元できないので、削除済み、失敗、未処理の束と残ったパスを表示して終了コード 2 を返す。
全件の原子的な削除や、削除直前の再確認後に外部プロセスが差し替えたパスの安全性は保証しない。
実行中の束へは他の実行者やメインセッションが書き込まない。

消すときは、作業ツリーの中のリンク(ジャンクションとシンボリックリンク)を先に探し、リンクだけを外してから消す。
探索と削除ではリンク先をたどらず、壊れたリンクもリンク自体だけを扱う。
リンクの解除に失敗した場合は、その束の通常ファイルを削除しない。
Windows では、別のプロセスが作業場所にしている空のディレクトリを消せないことがある。
通常ファイルとリンクがなく空のディレクトリだけが残った場合は、残ったディレクトリと Git の登録の有無を表示し、終了コード 0 を返す。
空かどうか確認できない場合やファイルが残った場合は終了コード 2 を返す。
作業ツリーと登録が既に両方ない束は、状態と定義を確認したうえで削除済みとして扱う。
片方だけが残る場合は、その束に対応するパスと登録だけを確認して再実行できるようにする。
対象外の登録も消す `git worktree prune` は使わない。
削除途中から再開するため、`.comment-tidy/work/<回>/clean-<束>.json` に束、基準、担当、準備時刻、作業ツリーのパスと削除進捗を保持する。
担当外の通常ファイルは削除対象側の属性で変換した基準の SHA-256、モード、種類を記録し、リンクはリンク先の文字列の SHA-256 と種類を記録する。
各パスの削除前に処理中のパスを保存し、削除後に削除済みへ移す。
再実行では削除済みか処理中のパスの欠落だけを許可し、残っている担当外ファイルのハッシュ、モード、種類と未追跡の内容を再確認する。
これにより、属性ファイルが先に削除されても照合の条件を保持する。
`run --fresh` で準備時刻が変わった束には以前の記録を適用せず、通常の確認から始める。
記録は片付け後にも証拠として残し、束の状態は変更しない。

通常ファイルを削除した後、空のディレクトリを下から片付け、対象の登録を `git worktree remove` で解除する。
空の残留により Git の解除が失敗した場合は、通常ファイルとリンクがないことを確認して作業ツリーの `.git` ファイルだけを外す。
ディレクトリを除去できた場合は、存在しないパスに対応する対象の登録だけを Git で解除する。
使用中の空のディレクトリが残る間は登録も残ることがあり、次の `clean` では登録の基準と状態を確認して対象だけを再処理する。

## テストの方針

- 字句解析は、言語ごとに移行元のテストを移植し、境界の例を足す。
- 検査と監査は、小さな基準と作業ツリーの組をテストの中で作って確かめる。git を使う経路は、一時ディレクトリに作ったリポジトリで確かめる。行末の変換が効くリポジトリ(`text=auto` と `core.autocrlf=true`)の例を必ず含める。
- `stats` は、CRLF、BOM、末尾の改行の無いファイル、各言語の例、doc コメントと区切り線を持たない言語(bat、CMake)、文字列だけの行と文字列の後ろにコメントが並ぶ行の数え方を確かめる。git を使う経路は一時ディレクトリのリポジトリで確かめる。
- `check --base` は、行末の変換が効くリポジトリ(`core.autocrlf=true`)で、コメントだけを変えた作業ツリーが合格することを確かめる。
- `check --offline` は、`node:child_process` を読み込んだ時点で例外を投げるように差し替えた状態で通し、子プロセスを起動しないことを確かめる。
- `privatize` は、移行元のテスト(13 件)を移植する。
- `run` は、作業ツリー、基準の写し、ハッシュの一覧、依頼文の用意と、`--fresh` の作り直しを確かめる。依頼文に禁止の語が入るときに止まることも確かめる。
- `delegate` は、委譲中の束が次に渡せる束に出ないこと、`--cancel` と `report` で解けることを確かめる。
- `report` は、窓口の最終報告の形(3 つの見出し、最後の JSON、`codex-agent:` の行)の例を流して、JSON の読み取り、監査行の有無、`warning=` の行の扱いを確かめる。
- `lint` は、規則ごとの当たる例と当たらない例、比べる元にある違反を報告しないこと、編集の範囲の外を `post-edit` が報告しないことを確かめる。フックの入口は、フックの JSON を標準入力へ流して確かめる。`git commit` の判定は、`git -C <dir> commit`、`&&` でつないだコマンド、`git commit-tree` のような別のコマンドの例を含める。検査の失敗で終了コードが 0 になることも確かめる。

## 実装の段階

新しいセッションで、次の順に進める。
各段階の終わりに相互レビューの 3 択を示す。

0. **準備**: `git init`、GitHub のリポジトリの作成、CodeGraph と ai-cross-review の導入と初期化(グローバルの CLAUDE.md の規則)。`package.json`、eslint、vitest の設定。
1. **核**: 字句解析(4 言語)、`stats`(`--compare` を含む)、`check`(字句の同一性、行数、行末、担当外の変更)。`check` の比較元は最初から「git のコミット」と「写しのディレクトリ」の 2 通りを抽象化し、`--offline` をこの段階で入れる。
   - **1a**: 字句解析(4 言語)、コメントのブロックと行数の数え方、`lint`(規則、報告するものの絞り込み、2 つのフックの入口、設定の無いリポジトリの既定値)、`install-hooks`。整理の回を待たずに使い始めるため、この部分を先に作る。フックの登録と、グローバルの CLAUDE.md のコメントの節を縮める作業は、開発者が `lint` の動きを確かめてから行う。
   - **1a の延長**: C# と TypeScript の字句解析を足し、`lint` の対象にする。1 言語ずつ足す。Python は docstring の扱いを決めてから、Rust は段階 2 以降に足す。
   - **1b**: `stats` と `check`。2 つの PR に分け、2 つ目を 1 つ目の上に積む。
     - **1b-1**: 時点の読み取り(`src/snapshot/`)と `stats`(`--compare` を含む)。読み取り口を、単純な使い手の `stats` で先に固める。
     - **1b-2**: `check`(4 つの不合格、2 つの警告、`--offline`)。設定の読み込みは `lint` のものを `maxLineWidth` と `docs` まで広げて使い、`scope`、`languages`、`areas` は段階 2 で足す。資料の参照の照合は `src/docs-refs.js` に置き、後で `refs` と `lint` も使う。
2. **設定と束**: 設定ファイルの読み込み(`stats`、`check`、`lint` を `scope` と `languages` に従わせることを含む)、`init` と判定基準の雛形、`plan`、作業の置き場と束の状態のモジュール、`prompt`、`status`。状態を書くコマンドは段階 3 で足すので、この段階の `status` は記録の無い束を「未着手」として出す。
3. **用意と取り込み(直列)**: `run`(作業ツリーと依頼文の用意)、`delegate`、`report`、`apply`。
4. **試行**: 小さなリポジトリで 1 束を、Agent ツールの `impl-standard` を経て最初から最後まで回す。確かめるのは、束の作業ツリーで Codex が書き込めること(`.comment-tidy/worktrees/` の下が信頼済みの作業ディレクトリとして扱われるか)、サンドボックスで `check --offline` が動くこと、行末の扱いである。
5. **並行と片付け**: 複数の束を並行に渡す運用の確認(同時に渡す数、利用上限での止まり方)と、`clean`。
6. **監査**: 既定の検査と誤りの型の検査、報告の JSON の集約。
7. **仕上げの道具**: `privatize`(C++)と `--report`、`--verify`、`branch`、`table`、`refs`、`residue`。
8. **スキルと資料**: グローバルのスキル、README、使い方。
9. **試行**: 実際のリポジトリで 1 回を最初から最後まで回し、既定値(重みの上限、同時実行の数)を見直す。

## 決定済みの事項

| 事項 | 決定 | 理由 |
|---|---|---|
| 配布の形 | 中央に置いた CLI を対象のリポジトリへ向けて実行する | `lint` がこの形でグローバルのフックから動いている。各リポジトリへ取り込むと、回の開始と終了のたびに PR が要る |
| 対象のリポジトリに追跡させるもの | `config.json` は恒久的に追跡する。判定基準と束の定義は回の間だけ追跡し、回が終わったら消す | `config.json` は `lint.allow` のために回の外でも要る。判定基準と束の定義は、レビューと別のセッションからの再開に要る |
| 実行者の既定と同時実行の数 | Agent ツールの `impl-standard`。同時に渡す束は 2 を目安にし、最初の試行で見直す。重みで定義を切り替えない | 直接起動はグローバルの規則で禁じられている。束の大きさは重みの上限でそろえている。3 つの窓口は利用上限を共有する |
| 対応する言語 | C++、JavaScript、CMake、bat に続けて、C# と TypeScript を `stats` と `check` より先に足す | `lint` は全リポジトリで動いており、C# と TypeScript のファイルを検査せずに通している |
| 他の言語の `privatize` | 対応しない(C++ だけ) | C# の `///` と TypeScript の `/** */` は IDE の表示にも使われ、非公開の宣言に付いていても害が小さい。その言語で回を回すときに判断する |
| 行の幅の扱い | 警告にとどめる | 不合格にすると、行を折り返して行数の上限に当たる向きに押す。幅の規約はリポジトリごとに違う |
| `refs` の置き場 | この道具のコマンドとして持ち、同じ判定を `lint` の見直し候補にも使う | 独立した道具にすると `docs.refPattern` を 2 か所に持つことになる。`lint` に入れれば回の後も使える |
| `lint` の確定の扱い | コミット前の検査で、確定の違反があればコミットを止める | 開発者が推奨の内容で進めるよう指示した |
| `lint` の英語だけのコメント | 検査しない | ツールの注記や名前空間の閉じの注記と見分けにくい |
| Codex の実行者からの `lint` | 実行者の定義へは足さない。コミット前の検査で拾う | `lint --changed` は git を起動するので、Codex のサンドボックスでは `spawn EPERM` で失敗する |

上の表は 2026-10-04 に開発者が決めた。`lint` の 3 件は 2026-10-02 に決め、Codex の実行者からの `lint` だけを、サンドボックスの制約が分かった 2026-10-04 に改めた。

## 開発者の判断が要る事項

| 事項 | この資料の案 | 別の案 |
|---|---|---|
| Python の docstring | `lint` と回の対象にしない(字句の上では文字列で、`#` のコメントだけを扱う) | docstring もコメントとして扱い、行数と規則を当てる |
